# ADR-0003：core/ 保持扁平文件结构，用文档化分层替代物理分包（方案 A）

- **状态**：Accepted（2026-10-09，用户批准「方案 A」；方案 B 仅在 Phase 1-3
  全部稳定且用户明确要求时作为独立分支重启）
- **日期**：2026-10-09
- **来源**：technical_roadmap Phase 2.4 + §3.3「子包划分与 PyInstaller 的
  连锁反应」、architecture_review_report §3.1 / 建议 P1-6

## 背景

架构审查指出 `core/` 24 个 .py 文件扁平堆放、无子包分层，「代码组织结构」
维度仅 2.5 分。审查报告的 P1-6 建议物理分包为 `core/engine/`、
`core/storage/`、`core/streaming/`、`core/infra/` 四个子包。

路线图 Phase 2.4 给出两个候选：

- **方案 A（保守，推荐）**：保持扁平文件，用文档化分层地图（即
  `docs/ARCHITECTURE.md` §2）替代物理分包；
- **方案 B**：物理分包 `core/engine/`(session,scheduler,resolver,taskops)
  `core/storage/`(registry,taskstore,persist,metacache,resume)
  `core/streaming/`(stream_server,preview,pieceview,inbound)
  `core/infra/`(config,logutil,secretbox,proxycheck,cache_*)，
  保留 `core/__init__.py` 兼容再导出。

关键约束是发布链路：本项目以 PyInstaller 打包为可分发的 Windows EXE
（onedir 为主、onefile 备用），`magnet-viewer.spec` 的 hiddenimports /
collect_submodules、`pack_check.py` 的产物路径断言、测试文件的 mock 路径
全部锚定当前扁平模块名。

## 决策

**采用方案 A**：不做物理分包。分层以文档形式固化为契约：

1. `docs/ARCHITECTURE.md` §2 的六层地图（基础/数据/逻辑/服务/编排/设施）
   + 依赖规则（只允许上层依赖下层、禁止反向、UI import 白名单）即分层
   的权威定义；
2. 各模块文件头注释继续承担「局部契约」职责（锁纪律、依赖方向定死、
   失败策略），文档承担「全局地图」职责；
3. 若未来重启方案 B：必须作为独立分支，同步更新 magnet-viewer.spec 的
   hiddenimports/collect_submodules + pack_check.py 路径断言 + 全仓
   `from core.x import` 语句 + 测试 mock 路径，并以 build.bat 出包 +
   pack_check 绿 + onedir 冒烟启动为验收（路线图 Phase 2.4 原文）。

## 否决方案 B 的论证（PyInstaller 连锁风险）

物理分包的破坏面是**四重连锁**，且每一环的回归都只有打包/真机才能暴露：

1. **全部 import 语句断裂**：24 个模块 × 全仓（core/ui/tests）引用点，
   改一处漏一处就是运行时 ImportError；
2. **spec 失配**：PyInstaller 的 hiddenimports/collect_submodules 按模块名
   收集，`core.session` → `core.engine.session` 后静态分析可能漏收，
   产物缺模块——源码测试全绿、EXE 打开才崩（pack_check 存在的理由正是
   这类「只有打开 exe 才会发现」的回归）；
3. **pack_check 产物路径断言失效**：自检脚本按 `_internal/...` 路径核对
   组件，分包后需同步重写；
4. **测试 mock 路径失效**：27 套回归里 `patch("core.fetcher.xxx")` 类
   字符串路径全部要改，改漏即测试假绿。

风险收益比不成立：分层收益（可读性、依赖约束）方案 A 已能拿到 90%——
真正缺的是「规矩」不是「目录」；而方案 B 引入的是发布链路的 P0 级风险
（路线图风险矩阵 R3：概率高(若选B)/影响高）。项目当前综合评分 2.8 的
主要短板在 fetcher 枢纽、main_window 巨块、异常层级，分包不解决其中任何
一项，反而让 Wave 1-3 的重构全部背上路径迁移税。

## 后果

- **正面**：零迁移风险；分层契约立即可执行（review 对照文档即可判违规）；
  Phase 2.4 的验证成本从「出包+冒烟」降为「文档评审」；
- **负面**：分层只存在于文档与纪律，无物理强制——新人可能继续往 core/
  扔文件而不看层级；越层 import 靠 Grep 门禁而非包结构自动拦截
  （Wave 0 基线 6 处 → Wave 2 前实测 9 处 → 2026-10-10 Wave 2 收敛为 0，
  见 ADR-0002 落地状态）；
- **缓解**：路线图量化目标表把「UI 越层 import = 0」列为可 Grep 验收的
  硬指标（已达成）；ARCHITECTURE.md 维护规则要求模块增删必须同步分层地图
  （2026-10-10 定稿：core/ 现为 26 个 .py 不含 `__init__.py`，新增
  interfaces.py / exceptions.py 已登记分层地图）。
