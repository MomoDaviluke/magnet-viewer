# ADR-0004：跨平台双轨策略——接受 Python/Kotlin 双实现，以行为契约保一致性

- **状态**：Accepted（现状接受 + 契约保障 Phase 4 实施中）
- **日期**：2026-10-09
- **来源**：architecture_review_report 第八章「跨平台架构」、
  technical_roadmap Phase 4 / §3.5

## 背景

桌面端（Python + PySide6 + libtorrent）与安卓端（Kotlin + Compose +
libtorrent4j）是**两套独立实现**，核心逻辑零代码复用：引擎管理
（session/fetcher ↔ BtEngine）、流媒体（stream_server ↔ StreamServer）、
任务操作（taskops ↔ TaskOps）、任务存储（taskstore ↔ TaskStore）、
缓存配额（cache_quota ↔ CacheQuota）均为各写一遍。审查报告「跨平台复用」
维度仅 2.0 分，并把「双轨维护」列为高风险（缺陷修两次，如 cache_guard
与 BtEngine 的同类锁问题在两端分别出现）。

两端目前唯一成体系的对齐手段：
- 主题语义对齐（Theme.kt 头注释明确「Palette.Light 就是桌面 ui/theme.py
  LIGHT 字典逐值对齐」）；
- 安卓各模块头注释逐处标注桌面对应位置（「桌面 core/scheduler.py 的
  Kotlin 移植」「与桌面 `_respond_503` 同语义」等，实证见 ARCHITECTURE.md §5）；
- 跨语言对拍夹具（android/tools/gen_parity_fixtures.py，13 组/155 条）
  冻结 PieceMap/连续前缀等纯逻辑语义。

## 决策

1. **接受双轨现状**，不强行统一语言。理由：
   - libtorrent 官方绑定只覆盖 C++/Python；安卓必须走 libtorrent4j
     （JNI 封装），不存在「一套 Python 跑两端」的现实路径；
   - 桌面 Qt Widgets 与安卓 Compose 的 UI 范式差异巨大，共享 UI 代码的
     成本高于重写；
   - 两端已各自成熟（桌面 25+ 套回归、安卓 150+ 单测），推倒重来风险
     远大于双写维护成本。
2. **以「行为契约」替代「代码共享」作为一致性保障**（Phase 4）：
   - `docs/contract_spec.md`：平台无关伪代码/流程图描述 6 大核心流程
     （磁力解析状态机、边下边播调度、Range 流服务语义、任务持久化/
     fastresume、缓存配额清理、主题令牌映射），每节标注桌面/安卓对应
     实现位置，两端实现后逐节互验，差异登记→修复或显式豁免；
   - `shared/task-schema.json`：任务记录字段/类型/必填的机器校验，两端
     各自加 ~30 行加载断言（不引入代码生成工具链——路线图 §3.5 判定
     其为过度工程）；
   - 差异靠审计流程发现（审计已实证登记 TaskOps.kt 头注释两处差异），
     不靠运行时同步。
3. **远期 Rust 共享核心：仅评估，设触发条件**。Phase 4.4 产出
   `docs/rust-eval.md`（libtorrent 双绑定现状、Rust 核心 + FFI 的成本收益、
   迁移路径草案），**不做实施**。重启评估→实施的触发条件（满足其一
   再议）：
   - 双轨同步成本实测超过契约维护成本（如单缺陷双端修复+回归的中位
     耗时持续 > 桌面端单独修复的 3 倍）；
   - 出现第三平台需求（macOS/Linux/iOS），双轨膨胀为三轨以上；
   - 安卓端逻辑缺陷密度显著高于桌面端且根因均为「移植走样」
     （contract_spec 比对差异清单连续两个季度不为零且集中于引擎层）。

## 后果

- **正面**：两端各自保持技术栈最优点（桌面 PySide6 快速迭代、安卓原生
  体验）；契约文档让「行为一致」第一次变成可评审、可比对的显式目标，
  而非口口相传；
- **负面**：双写维护成本继续存在——每个核心 bugfix 要问「安卓端有没有
  同型缺陷」（审计文化已制度化这一问）；契约文档本身需要维护，流程图
  与代码脱节会误导；Android CI 目前仅构建、无单测执行（Phase 3.3 接入前，
  安卓侧回归靠本地 gradlew test）；
- **约束**：任何新增跨端行为（状态机取值、503 语义、诊断头、配额保护
  名单）在改动一端时**必须**同步检查另一端与 contract_spec.md；
  对拍夹具覆盖的纯函数语义（PieceMap 换算等）改动前必须先改夹具基线。
