# ADR-0001：锁纪律与单锁归属

- **状态**：Accepted（2026-10-09 文档化确认；纪律本体自 fetcher 重构阶段 3 起生效）
- **日期**：2026-10-09
- **来源**：`core/registry.py` 文件头注释、`core/scheduler.py` 线程安全节、
  `core/preview.py` 锁纪律节、full_audit_report_2026-09-29 P3（R-10 锁序边）、
  architecture_review_report §4

## 背景

多任务下载引擎天然是多线程场景：GUI 线程（tick/seek/begin/用户操作）、
libtorrent alert 后台线程（元数据就绪/完成告警）、HTTP 流服务请求线程
（每 50ms 探测可用性 + 点播补拉）、shutdown 线程（stop）。任务状态
（注册表 `torrents`、清单 `tasks`、当前别名组）被这些线程并发读写。

历史上出过真实缺陷（R-1）：告警线程里**裸写** `self._resolving`（不持锁），
与主线程锁内读写交错。同时，若每个子系统各持各的锁，锁之间一旦形成环路
就是死锁；若用可重入锁（RLock）则可以嵌套取锁，但会掩盖「持锁期间做了
什么」这一关键信息，锁边界越来越模糊。

审计（2026-09-29 P3）还发现一处锁序边：taskops 在 `reg.lock` 段内调
`scheduler.stop()`，形成 `reg.lock → scheduler._lock` 的跨对象持锁调用，
与调度器「锁序末端、锁内绝不取注册表锁」的决策冲突（R-10）。

## 决策

1. **单锁归属**：`TaskRegistry` 持有全项目**唯一任务锁**
   （`self.lock = threading.Lock()`，不可重入）。SessionManager 的 `_lock`
   只是它的 property 代理；taskops / resolver / preview / session 一律借用
   这一把锁，不再各自新增任务级锁。
2. **`*_locked` 命名纪律**：「一次调用一个锁段」——公开方法**自持锁**；
   名字以 `_locked` 结尾的版本要求调用方**已持锁**（用于复合临界区）。
   两者绝不互相嵌套调用（不可重入锁嵌套即自死锁，这个「失败模式」反过来
   就是纪律的强制执行机制）。
3. **锁序单向**：`reg.lock` → `scheduler._lock` → `PieceView._lock`。
   scheduler 是锁序末端，其锁段内绝不取 reg.lock / 落盘 / 任何 I/O。
   PreviewCore 的 `_views_lock`、PieceView 的锁都是**叶子锁**：持有时绝不
   调用会取其他锁的方法。
4. **跨对象停调度出锁执行**（R-10 修复形态）：需要「持 reg.lock 改状态 +
   停 scheduler」时，锁内只记标志，**出锁再调** `sched.stop()`
   （taskops.py remove_task L434-444 记标志 / L473-476 出锁再停、
   set_focus L541-550 同款；行号为 2026-10-10 实测）。
5. **不可重入链的取舍**：接受「锁内不得调用任何会取锁的方法」带来的
   编写约束（begin/seek_to_byte 必须在调 `self.tick()` 之前放锁，否则
   tick 的非阻塞取锁必然失败、首窗预约静默丢失），换取锁边界显式可读。
   该不变式由 `concurrency_test.py §F` 静态检查钉住（扫描 `@_exclusive`
   装饰与显式 `with self._lock` 两种形态）。
6. **锁内禁 I/O**：任务锁段内禁止落盘/fsync/remove_torrent 等阻塞调用；
   `tasks()` 锁内只做字典浅拷贝，libtorrent 绑定调用出锁派生（R-3）。
   scheduler 锁内的非阻塞状态变更调用（set_piece_deadline 等）是**登记在案
   的例外**，前提「锁内只做非阻塞状态变更、私有短锁、热路径非阻塞取锁
   跳过本拍」；一旦引入阻塞调用例外即失效。

## 后果

**正面**：
- 死锁面收敛为「一条单向锁序链」，可静态检查、可测试锁定；
- `*_locked` 后缀让「此处调用方须持锁」在函数名上自解释，review 可查；
- 锁持有时间可度量（registry `tasks()` 从 N×句柄往返降为一次字典拷贝；
  scheduler 私有锁实测最坏 ≈1ms）。

**负面 / 代价**：
- 不可重入锁要求编写者时刻警惕嵌套——公开方法内调 `*_locked`、或
  `*_locked` 内调公开方法都会自死锁，必须靠纪律 + 测试兜底；
- 「出锁再停调度」这类修复让个别操作变成两步（锁内改状态、锁外停调度），
  中间窗口存在短暂的不一致（如 stop 之前的一次 tick 读到新焦点句柄），
  需论证该窗口无害（轮询本就按焦点容错）；
- 读探针（tail_ready/buffer_progress 等）刻意不加锁，最坏返回一次陈旧值，
  下一拍（700ms）修正——接受展示层的短暂陈旧，换取 HTTP 高频轮询
  不卷进锁车队。
